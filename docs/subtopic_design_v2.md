# 서브토픽 설계 v2 (탐색 관점 모델)

2026-08-20 재정의. 기존 구현(`src/topic_classifier` 의 `SUBTOPICS_ENABLED` 경로)과는
**전제가 다르다.** 기존은 이벤트를 하나의 갈래에 배정하는 *분류* 였고, v2 는 같은 이벤트를
여러 갈래에서 다시 보여주는 *탐색* 이다. 옛 구현을 고쳐 쓰는 게 아니라 새로 짠다.

| | v1 (보류 상태) | v2 (이 문서) |
|---|---|---|
| 귀속 | 단일 — `events.topic_id` 가 leaf 서브토픽을 가리킴 | **다중** — 한 이벤트가 여러 서브토픽에 동시 소속 |
| 생성 시점 | 이벤트 유입마다 assign-or-create | 토픽 이벤트가 임계치에 도달했을 때 **전체를 보고 일괄 생성**, 이후 증분 |
| 미소속 이벤트 | 없음(항상 어딘가 배정) | **단독 이벤트** 로 별도 관리 |
| 관점 축 | 쟁점 축 하나 | 대상 / 역할 / 토픽 고유 + 결합 |

## 1. 정의

서브토픽은 이벤트를 하나의 기준으로 나누는 분류 단위가 **아니다.**
사용자가 하나의 토픽을 여러 관점에서 탐색하도록 관련 이벤트를 묶어 보여주는 **탐색 단위**다.

따라서 하나의 이벤트는 여러 서브토픽에 동시에 포함된다.

```
Topic: 올림픽
  Event: 양궁 여자 단체 금메달 / 양궁 남자 개인전 동메달 / 대한민국 메달 순위 2위

  양궁      → 여자 단체 금메달, 남자 개인전 동메달
  대한민국  → 여자 단체 금메달, 남자 개인전 동메달, 메달 순위 2위
  경기 결과 → 여자 단체 금메달, 남자 개인전 동메달
```

`양궁 여자 단체 금메달` 은 세 서브토픽 모두에 들어간다. 같은 토픽이라도 사용자마다
찾는 축(대상 / 쟁점 / 사건 성격)이 다르기 때문이다.

## 2. 생성 시점

토픽 내 이벤트가 임계치에 도달하면 최초 생성 로직을 돌린다.

| 환경 | 임계치 | 근거 |
|---|---|---|
| 서비스 | 이벤트 **7개** | 이 정도부터 목록 훑기가 부담이 된다 |
| 실험 | 이벤트 **3개** | 현재 데이터셋에 7개 이상 토픽이 거의 없어 검증이 불가능 |

## 3. 생성·귀속 절차

### 3.1 최초 생성

토픽 내 **전체 이벤트**를 한 번에 보고 의미 있는 탐색 관점을 찾는다. 관점마다 서브토픽을
만들고 관련 이벤트를 전부 귀속한다(다중 귀속). 어느 관점에도 자연스럽게 들어가지 않고
새 관점을 만들 만한 공통성도 없는 이벤트는 **단독 이벤트**로 둔다.

### 3.2 신규 이벤트 유입

```
1. 기존 서브토픽 귀속 여부 판단
2. 귀속 가능한 "모든" 기존 서브토픽에 귀속
3. 토픽 전체 이벤트 기준으로 새 탐색 관점 형성 여부 판단   ← 2와 독립
     ├ 형성됨 → 새 서브토픽 생성 + 관련 기존 이벤트까지 함께 귀속
     └ 아님   → 생성 안 함
4. 2·3 어디에도 안 들어갔으면 단독 이벤트
```

**3은 2의 결과와 무관하게 항상 수행한다.** 신규 이벤트가 기존 서브토픽에 이미 들어갔더라도,
그 이벤트 때문에 새 관점(예: 판정 논란)이 성립할 수 있기 때문이다.

### 3.3 단독 이벤트

별도의 `단독 이벤트` 탐색 메뉴로 제공한다. 억지 서브토픽을 만들어 탐색성을 떨어뜨리지 않기
위한 장치다. 고정 상태가 아니라서, 나중에 관련 이벤트가 쌓여 관점이 생기면 그 서브토픽으로
편입되고 목록에서 빠진다.

## 4. 생성 원칙

1. **의미 있는 탐색 관점이어야 한다.** 사용자가 그 관점만 골라 보고 싶을 만큼이어야 한다.
   현재 이벤트가 하나뿐이어도, 관점 자체가 의미 있고 후속 이벤트가 사회적 흐름상 충분히
   예상되면 만들 수 있다. **판단이 애매하면 단독 이벤트로 둔다.**
2. **기존 서브토픽과 구별되는 관점이어야 한다.** 포함 이벤트가 같아도 관점이 다르면 공존한다
   (`양궁` / `메달`). 반대로 이벤트 구성이 달라도 관점이 실질적으로 같으면 만들지 않는다
   (`대한민국` / `한국`).
3. **이름만으로 포함될 이벤트를 예측할 수 있어야 한다.** 모호하거나 의미가 불분명한 이름은 쓰지 않는다.

## 5. 관점의 세 방향

배타적 분류가 아니라 관점을 **발견하기 위한** 축이다. 실제 서브토픽은 결합형이 흔하다.

### 5.1 대상 기반
인물·국가·단체·종목·정책 등 대상 자체가 독립적 탐색 가치를 가질 때. 예: `대한민국`, `양궁`,
특정 선수, `트럼프-이재명`(관계 자체가 관점일 때 결합 가능).
등장했다는 이유만으로 모든 대상을 만들지는 않는다.

### 5.2 역할 기반
여러 토픽에서 반복 사용 가능한 범용 관점. 아래 역할 사전을 참고하되, 역할명만으로 의미가
부족하면 대상·쟁점을 붙여 구체화한다(`논란` → `판정 논란`). 사전의 표현을 그대로 쓸 의무는 없다.

### 5.3 토픽 고유
사전이나 대상만으로 설명되지 않지만 그 토픽에서 공통 쟁점·사건 흐름이 발견될 때.
예: `투표소 용지 부족과 현장 대응`, `선관위 책임 문제와 후속 조치`, `개막식 국가명 오표기`.

### 5.4 결합
`판정`+`논란` → `판정 논란` / `의료계`+`반응` → `의료계 반응`.

## 6. 역할 분류 사전 (17개)

참고 사전이지 정답 목록이 아니다. 여기 없는 관점도 만들 수 있다.

### 전개
| 역할 | 기준 | 경계 |
|---|---|---|
| 원인·배경 | 사건이 발생하게 된 이유·계기·이전 배경 | 이후 결과·영향은 제외 |
| 결과 | 사건·활동·결정 뒤 확정된 결과 (결정/경기/선거/협상 결과, 성과, 기록) | 파급 변화 → 영향, 이후 대응 → 후속 조치 |
| 영향 | 다른 대상·상황에 미친 변화·파급 효과 | 사건 자체 결과 → 결과, 의도적 대응 → 후속 조치 |
| 후속 조치 | 이후 대응으로 취해진 조치 (재발 방지, 책임자 사퇴, 재검표, 제도 개선) | 자연 파급 → 영향, 단순 표명 → 입장·반응 |

### 성격
| 역할 | 핵심 | 경계 |
|---|---|---|
| 논란 | **무엇이 문제인가** | 단순 의견 차이·반대만으로는 논란이 아니다 |
| 의혹 | **사실인지 아직 확인되지 않은 문제 제기** | 사실이 확인된 사건은 의혹이 아니다 |
| 갈등 | **누구와 누가 대립하는가** | 사안 자체가 문제 → 논란, 미확인 주장이 핵심 → 의혹 |
| 피해 | 개인·집단·사회에 발생한 손실 (인명·재산·경제·사회적) | `영향` 보다 피해에 초점 |

### 입장·반응
| 역할 | 기준 | 경계 |
|---|---|---|
| 입장 | 주체가 견해·태도·방침을 밝힌 것 | 선행 사건에 대한 대응일 필요 없음 |
| 반응 | 선행 사건·발언에 대응한 말·행동 (지지, 반대, 비판, 반발, 항의, 환영, 해명, 사과, 요구) | **선행 사건과의 대응 관계가 존재**한다는 점이 입장과 다르다 |

### 행위
개별 절차를 전부 사전화하지 않고, 여러 세부 사건을 하나의 흐름으로 포괄하는 범용 행위만 둔다.

| 역할 | 기준 | 경계 |
|---|---|---|
| 협상 | 조건·이해관계를 조율해 합의점을 찾는 **과정** | |
| 합의 | 공통 결론·약속에 도달한 **내용과 성립** | 과정 → 협상 |
| 조사 | 사실관계·원인 확인 절차 (행정조사, 진상조사, 감사) | 형사 절차 → 수사 |
| 수사 | 범죄 혐의에 대한 수사기관 절차 (압수수색, 소환조사) | 일반 확인 → 조사, 법원 단계 → 재판 |
| 재판 | 법원 심리·판단 절차 (공판, 심문, 판결, 선고, 항소) | |
| 시위·집회 | 주장·요구·항의를 위한 공개 결집과 직접 연결된 현장 사건 | |
| 파업 | 집단적 업무 중단·거부 (예고, 돌입, 지속 및 직접 연결된 사건) | |

### 공통 원칙
- 여러 토픽에서 반복 활용 가능한 **범용** 관점이어야 한다.
- `진행`·`위기`·`전망`·`예정` 처럼 시간에 따라 의미가 변하는 동적 상태는 역할로 쓰지 않는다.
- 지나치게 구체적인 개별 행위·절차는 상위 역할로 포괄한다.

## 7. 이름 구성

- 이름만으로 탐색 범위가 짐작되게 쓴다.
- 역할명만으로 부족하면 대상·쟁점을 결합한다: `협상 결과`, `의료계 반응`, `선거 부정 의혹 수사`.
- 불필요하게 길거나 개별 이벤트를 그대로 요약한 이름은 쓰지 않는다.
- 시간 구분(`첫째 날`, `N일차`)이나 기사 논조(`찬성`/`반대`)로 이름 짓지 않는다.

## 8. 구현상 따라오는 것

- **스키마**: 다중 귀속이라 `events.topic_id` 단일 FK 로는 표현할 수 없다. `subtopics` +
  `subtopic_events`(M:N) 가 필요하다. v1 의 `topics.parent_topic_id` 재사용은 검토 대상이지
  전제가 아니다.
- **평가**: 정답이 "이벤트 → 서브토픽 1개"가 아니라 집합 대 집합이므로, 기존 must/cannot 쌍
  지표를 그대로 쓸 수 없다. 관점 이름의 타당성과 귀속 재현율·정밀도를 따로 봐야 한다.

실험 하네스: `eval/subtopic_v2_harness.py` (스냅샷 JSON 입력, DB 불필요, 로컬 Ollama 사용)

### 확인된 것

1. **토픽 품질이 서브토픽 품질의 상한이다.** a1/a2 는 프롬프트를 고쳐도 좋아지지 않았다.
   입력 토픽 1543(뉴욕증시 + 트럼프 통화 + FIFA + 러시아 공격)에는 공통 관점이 존재하지
   않아서, 모델이 이벤트마다 서브토픽을 하나씩 만드는 것 말고 할 수 있는 게 없었다.
   토픽을 다시 묶고(b 계열) 나서야 프롬프트 개선이 지표에 반영됐다.
2. **한 번의 호출로는 과분할과 다중 귀속을 동시에 못 잡는다.** 개수 상한을 늘리면 다중 귀속은
   살지만 이벤트 1개짜리 서브토픽이 61% 까지 오르고(b1), 상한을 조이면 과분할은 줄지만
   다중 귀속이 15% 로 무너져 단일 귀속으로 회귀했다(b2).
3. **관점 발견과 귀속을 나누면 둘 다 잡힌다.**(b4) 2단계의 핵심은 2단계를 **이벤트 기준**으로
   묻는 것이다("이 이벤트는 어느 서브토픽들에 속하나"). 서브토픽 기준으로 물으면 한 관점을
   채우고 다음으로 넘어가느라 같은 이벤트를 다시 집어넣지 않는다.

| b6 | b5 + 관점 정제 | 24 | 1.56 | 52.1% | 0.0% | 20.8% | 37.5% | 41.7% |

| i2 | 증분, 단계 분리 | 36 | 2.10 | 64.6% | 0.0% | 36.1% | 36.1% | 47.2% |

**b5 가 현재 최선이다.** 일괄 생성은 `--mode two-stage --membership per-event` 를 기본으로 삼는다.

#### 확인된 것 (이어서)

4. **귀속은 이벤트 하나씩 물어야 한다.** b4→b5 에서 1건짜리 서브토픽이 28.6%→11.1%,
   다중 귀속이 37.5%→68.8% 로 함께 개선됐다. 이벤트 목록을 한 번에 훑으면 주변 이벤트에
   끌려가 오귀속이 생기고(b4 의 "반공 메시지 강조"), 판단 대상이 하나면 그 끌림이 사라진다.
   호출은 이벤트 수만큼 늘지만 로컬에서는 감당할 수 있는 비용이다.
5. **관점 정제(b6)는 실패했다.** 포함관계는 29.6%→37.5% 로 오히려 나빠졌고 다중 귀속이
   68.8%→52.1% 로 무너졌다. 30B 가 "실질적으로 같은 관점인가"를 판단하지 못하고 그냥 합친다 —
   `당내 주자 경쟁` 이 `장애 당사자 준비 지원` 을 흡수했고, `한국의 진출 여부` 가
   `아시아 예선 결과의 영향` 을 삼켰다. 구체적 관점명이 죽고 이벤트 요약형 이름이 남아
   이름 품질도 33.3%→41.7% 로 나빠졌다. **`--refine` 은 기본 off 로 두고 쓰지 말 것.**
   포함관계는 합칠 대상이 아니라 **지표로 띄우고 사람이 판단할 것**이다(설계상 위반이 아니다).
6. **증분의 단계 분리는 옳았다.** i1→i2 에서 다중 귀속이 37.5%→64.6% 로 올라 일괄(68.8%)에
   근접했다. 원인은 응답 형식이었다 — `{서브토픽: 이벤트들}` 로 물으면 서브토픽 기준으로
   훑게 되어 이미 한 곳에 넣은 이벤트를 다른 곳에 다시 넣지 않는다. 귀속은 이벤트 기준으로
   묻고(`build_single_event_membership_prompt`), 새 관점 판단은 별도 호출로 분리한다
   (`build_new_perspective_prompt`). 설계 5.2 의 "3단계는 2단계와 독립"이 문구가 아니라
   호출 분리로 보장된다.

#### 3차 실험 — 지표가 놓치고 있던 축

**"b5 가 최선" 이라는 2차 결론은 불완전한 지표에 근거했다.** 커버율(한 서브토픽이 토픽
이벤트의 몇 %를 담는가)을 추가하고 나서 순위가 뒤집혔다.

| run | 서브토픽 | 토픽의 60% 이상을 담는 것 | 1건짜리 | 막다른 이름 |
|---|---|---|---|---|
| b4 (귀속 batch) | 69 | 32% | 31.9% | 17.4% |
| b5 (귀속 per-event) | 67 | **49%** | 13.4% | 3.0% |
| c-b (서비스 기준, 억제 전) | 15 | 40% | 6.7% | 6.7% |
| **c-b2 (넓은 관점 억제)** | 23 | **13%** | 26.1% | 17.4% |

per-event 귀속은 다중 귀속과 과분할을 개선했지만 그 대가로 관점이 넓어졌다. 이벤트를
하나씩 보면 넓은 이름에는 무엇이든 맞아 보이기 때문이다. c-b 의 18건 토픽
"장애인 고용 및 복지 정책 동향" 아래 `법제 정비 동향` 하나가 15건(83%)을 담았는데,
거기에 AI 고용서비스 협약·기능경기대회·통합돌봄까지 들어갔다. 토픽 이름을 바꿔 말한
서브토픽은 눌러도 목록이 그대로라 탐색 단위가 못 된다.

7. **넓은 관점은 귀속 단계에서 막을 수 없다.** 관점을 정하는 단계에서 좁혀야 한다.
   "토픽 이름을 바꿔 말한 이름은 만들지 말 것" 에 구체 예를 붙이고(`법제 정비 동향` 은 너무
   넓고 `고용 의무 미달과 부담금` 이 적정), 귀속 쪽에 "같은 토픽의 다른 이벤트에도 똑같이
   들어맞는 이유라면 고를 근거가 아니다" 를 넣었다. 60% 이상을 담는 서브토픽이 40%→13% 로
   내려갔고 15건짜리 거대 서브토픽이 사라졌다.
8. **두 극단은 서로를 밀어낸다.** 관점을 넓히면 토픽 자체가 되고, 좁히면 이벤트 요약이 된다
   (c-b→c-b2 에서 60%+ 는 40%→13% 로 좋아졌지만 1건짜리가 6.7%→26.1% 로 나빠졌다).
   설계 문서 4장은 1건짜리를 허용하지만(관점이 의미 있고 후속 이벤트가 예상되면 생성 가능)
   토픽 전체를 담는 것은 원칙 2(기존과 구별되는 관점)에 어긋나므로, **c-b2 쪽이 맞다.**

##### 지표를 고친 이력 (지표가 틀리면 결론이 틀린다)

- `widest_coverage` / `wide_ratio` 추가 — 1건짜리 과분할만 재고 반대쪽 극단을 안 재서
  b5 를 최선으로 잘못 뽑았다.
- `event_echo_ratio` 를 **1건짜리 서브토픽에 한해서만** 세도록 정정 — `장애여성 모성권 보장`(2건)
  처럼 이벤트 제목과 어휘가 겹쳐도 정상인 관점을 오탐했다. 이름 요약형이 해로운 이유는
  "다음 이벤트가 들어올 자리가 없다" 인데, 이미 여러 이벤트가 모였다면 그게 반증된다.
- `alignment()` 추가 — 증분과 일괄을 지표별로 나란히 놓는 것만으로는 "같은 구조에 도달했는가"를
  알 수 없다. 서브토픽을 이벤트 집합으로 보고 양방향 최대 자카드를 평균한다.

#### 증분: seed 를 서비스 기준으로 올려도 폭증은 그대로

2차에서 "seed 가 빈약해서 이후가 오염된다" 고 봤는데, seed 를 3→7 로 올린 c-i 에서 반증됐다.

| | 증분(seed 7) | 일괄 |
|---|---|---|
| 서브토픽 | 28 | 9 |
| 1건짜리 | 21.4% | 0.0% |
| 구조 일치도 | 0.503 | — |

같은 40건에서 증분이 서브토픽을 3배 넘게 만든다. 원인은 seed 가 아니라 **정리 단계의 부재**다.
증분은 관점을 추가만 하고 없애지 않는다.

#### 4차 — 재현성이 먼저였다

3차까지의 A/B 비교는 **전부 단일 실행**이었고, 온도를 한 번도 지정하지 않아 ollama 기본값(0.8)으로
돌고 있었다. 같은 입력·같은 설정으로 일괄 생성을 두 번 돌려 보고서야 그게 드러났다.

| | 재현성(구조 일치도) | 서브토픽 | 60%+ | 1건짜리 | 다중 귀속 | 막다른 이름 |
|---|---|---|---|---|---|---|
| temp 0.8 (그동안) | 0.537 | 23 / 18 | 13% / 28% | 26.1% / 5.6% | 48.1% / 50.0% | 17.4% / 0.0% |
| **temp 0** | **1.000** | 20 / 20 | 10% / 10% | 25.0% / 25.0% | 25.9% / 25.9% | 5.0% / 5.0% |

9. **"증분이 일괄에 수렴하지 않는다" 는 판단은 틀렸다.** 증분과 일괄의 구조 일치도(0.532~0.548)는
   **일괄을 두 번 돌렸을 때의 일치도(0.523~0.537)와 같다.** 0.55 는 증분의 결함이 아니라
   비결정성이 만든 측정 천장이었다. 증분은 일괄만큼 일관적이다.
10. **재현성이 없으면 어떤 개선도 측정할 수 없다.** 3차의 "넓은 관점 억제로 60%+ 가 40%→13%" 도
    재실행에서 28% 가 나왔으므로 개선이라 단정할 수 없다. 온도를 지정하지 않은 채 지표 몇 %p 를
    비교한 것이 이 실험의 가장 큰 방법론적 결함이었다.
11. **temp 0 은 다중 귀속을 희생시킨다.** 48%→25.9%. 온도가 높으면 모델이 더 많이 고르는데
    그게 v2 의 핵심 가치였다. 재현성 없이는 측정 자체가 불가능하므로 **temp 0 을 기준으로 삼고,
    다중 귀속은 온도가 아니라 프롬프트로 되찾는다.**

`--temperature` 를 추가하고 **기본값을 0 으로** 했다(`subtopic_v2_harness.py`, `subtopic_v2_incremental.py`).
앞으로 지표를 비교할 때는 온도를 명시할 것.

#### 5차 — temp 0 에서 다시 잰 결론

재현성 1.000 이므로 아래 차이는 전부 설정·프롬프트 효과다.

| temp 0 | 서브토픽 | 이벤트당 귀속 | 다중 귀속 | 60%+ | 구조 일치도 |
|---|---|---|---|---|---|
| 일괄 (절차 강제 전) | 20 | 1.22 | 25.9% | 10% | — |
| **일괄 (절차 강제 후)** | 22 | **1.41** | **42.6%** | 9% | — |
| 증분 (정리 없음) | 28 | 1.90 | 70.0% | — | 0.557 |
| **증분 (5걸음 정리)** | **17** | 1.45 | 42.5% | — | **0.693** |

12. **recompact 는 효과가 있다.** temp 0.8 에서 0.532→0.548 로 미미해 보였던 것이, 온도를 잡으니
    0.557→0.693 으로 뚜렷해졌다. 서브토픽도 28→17 로 일괄(14) 수준까지 내려온다.
    4차에서 "수렴도를 못 올린다" 고 본 것은 노이즈 때문이었다.
13. **다중 귀속은 결과가 아니라 절차를 지시해야 나온다.** "들어맞는 것을 모두 고르세요" 는
    temp 0 에서 작동하지 않는다(첫 매칭에서 멈춘다). "목록을 처음부터 끝까지 훑고, 하나 찾았다고
    거기서 멈추지 마세요" 로 바꾸자 이벤트당 귀속이 1.22→1.41, 다중 귀속이 25.9%→42.6% 가 됐다.
    넓은 관점 지표(60%+)는 10%→9% 로 그대로여서, 정확도를 깎지 않고 누락만 줄였다.
14. **다중 귀속률은 단독으로 읽으면 안 된다.** 서브토픽 수에 끌려다닌다 — 증분(정리 없음)의 70% 는
    품질이 좋아서가 아니라 관점을 28개나 만들어서다. `이벤트당 귀속 수`와 함께 볼 것.

15. **최종 설정에서 증분은 일괄과 같은 수준에 도달한다.** 서브토픽 17 vs 16, 이벤트당 귀속
    1.55 vs 1.40, 다중 귀속 45.0% vs 42.5%. 증분 경로는 이제 검증된 것으로 본다
    (구조 일치도 0.638 — 비결정성 천장이 사라진 temp 0 기준이라 값 자체보다 규모·특성의
    일치가 판단 근거다).

#### 6차 — 재생성 안정성 (서비스 적용을 막고 있던 것)

온도 0 이면 같은 입력에 같은 결과가 나오지만, **이벤트가 한 건이라도 늘면 이름이 거의 다 바뀐다.**
각 토픽에서 마지막 이벤트 1개를 뺀 "어제 상태" 를 만들어 재보니 그랬다.

| | 어제 대비 구조 일치도 | 이름 유지 |
|---|---|---|
| 그냥 재생성 | 0.749 | **9/21** |
| **기존 구조 이어받아 재생성** | **0.929** | **21/21** |

18건 토픽에서 `장애인 교육권 차별 대응` 이 사라지고 `장애인 고용 기술 혁신` 이 생기는 식이었다.
서비스에서 이는 사용자가 어제 클릭하던 서브토픽이 오늘 없어진다는 뜻이라, 주기적 재생성 전략
자체를 무너뜨린다.

16. **재생성할 때 현재 구조를 컨텍스트로 넘기면 해결된다.** "여전히 유효한 관점은 한 글자도 바꾸지
    말 것 / 새 이벤트 때문에 새 관점이 생겼을 때만 추가 / 해당 이벤트가 사라졌을 때만 제거".
    이름 유지가 9/21 → 21/21 이 됐다.
17. **반응성은 잃지 않았다.** 새로 들어온 이벤트 3건이 모두 적절한 서브토픽에 자리잡았고 단독으로
    밀려나지 않았다(엔화 → `환율 고착화와 리스크 확대`, 트럼프-시진핑 → `외교적 상징성과 정상회담
    재개 시도`). 기존 이름을 주면 관성이 생겨 새 관점을 못 만들까 우려했으나 그렇지 않았다.
18. **대가는 넓은 관점이 는다는 것.** 토픽의 60% 이상을 담는 서브토픽이 9%→19% 로 늘었다.
    어제 관점을 붙들면서 새 이벤트가 기존의 넓은 관점에 흡수되기 때문이다. 반면 1건짜리는
    27.3%→19.0%, 막다른 이름은 9.1%→4.8% 로 좋아졌다. 안정성 이득이 훨씬 크므로 이어받기를 켠다.
    넓어지는 것은 별도 주기의 관점 재검토로 관리할 문제다.

증분의 `--recompact` 도 같은 방식으로 현재 상태를 넘긴다 — 정리 단계가 곧 재생성이라 같은 결함을
안고 있었다.

#### 이름 유지와 관점 정리는 양립하지 않는다 (미해결)

증분의 `--recompact` 에 이어받기를 적용하자 정리 효과가 사라졌다.

| temp 0, 3토픽 40건 | 서브토픽 | 이벤트당 | 1건짜리 | 재생성 시 정리 |
|---|---|---|---|---|
| 정리 없음 | 28 | 1.90 | 28.6% | — |
| 정리, 이어받기 없음 | **17** | 1.55 | 17.6% | 8→5, 10→4, 8→5 |
| 정리 + preserve | 22 | 1.90 | 27.3% | 8→7, 12→8, 8→7 |
| 정리 + consolidate | 22 | 2.40 | **13.6%** | 8→7, 11→8, 8→7 |

`consolidate` 는 정리 전용 문구를 따로 준 것이다("겹치는 관점은 합치고, 1건짜리로 더 늘 것 같지
않은 것은 빼되, 남기는 것의 이름은 바꾸지 마세요"). 1건짜리는 27.3%→13.6% 로 흡수했지만
**관점 수 자체는 줄이지 못했다.** "이름을 바꾸지 말라" 와 "합쳐서 줄여라" 가 충돌하고 30B 가
둘 다 만족시키지 못한다. b6 와 같은 성질의 실패지만, 그때처럼 무관한 관점을 합치는 오작동은
없었고 그냥 안 합칠 뿐이다.

**현재 판단**
- **주기적 전체 재생성에는 이어받기(preserve)를 켠다.** 이득이 압도적이다(이름 유지 9/21→21/21).
- **증분의 recompact 는 트레이드오프로 남긴다.** 이어받기를 켜면 이름이 유지되는 대신 관점이
  22개까지 쌓이고, 끄면 17개로 정리되는 대신 이름이 바뀐다. 어느 쪽이 나은지는 실제 탐색 화면과
  사용 로그를 봐야 정할 수 있다.
- **정리를 강하게 하려면 LLM 이 아니라 규칙이 필요하다.** 판단이 필요한 병합("이 둘은 같은
  관점인가")은 로컬 30B 의 능력 밖이라는 것이 b6 와 여기서 두 번 확인됐다. 반면 "A 의 이벤트
  집합이 B 에 완전히 포함된다" 같은 판정은 코드로 결정적으로 할 수 있다. 다만 설계 4장이
  "구성이 같아도 관점이 다르면 공존" 을 허용하므로 자동 삭제는 위험하고, 후보를 뽑아 사람이
  확인하는 형태가 맞다.

#### 7차 — 귀속 적합률을 처음으로 쟀다 (강모델 감사)

지금까지의 지표는 전부 구조(개수·비율)만 쟀고 "이 이벤트가 이 이름에 맞는가" 는 재지 않았다.
그래서 지표는 개선되는데 결과물은 그대로인 상태를 알아채지 못했다. sonnet 이 사용자 관점에서
(서브토픽, 이벤트) 쌍마다 판정하고("이 이름을 클릭한 사용자가 이 이벤트를 보고 '왜 이게 여기
있지?' 하면 부적합, 확신 없으면 부적합"), opus(high) 가 같은 이벤트로 정답 구조를 독립 생성했다.
결과: `eval/results/subtopic-claude-audit.json`

**t0-c(확정 설정)의 실제 귀속 적합률: 35/76 = 46.1%.** 절반이 사용자 관점 판정을 통과하지 못한다.

    `근로지원인·업무지원인 제도`, `다수당 의장단 독식 논란`. 로컬 30B 의 이름은 추상적 주제어다 —

    닻이 있는 이름이어야 귀속도 조여진다.
20. **구조 지표와 품질 지표는 독립이다.** t0-c 는 구조 지표(커버율 9%, 1건짜리 27%, 재현성 1.0)

#### 7차 후속 — 진단(opus, xhigh)과 처방

진단 전문: `eval/results/subtopic-claude-audit.json` (감사·정답 원본 포함)

**지배적 실패는 2단계(귀속)다.** 로컬 이름이 정답 축에 대응하는 서브토픽 안에서도 적합률이
52.9%(27/51) — 관점을 완벽히 뽑아도 현재 귀속 방식의 상한이 53% 라는 뜻이다. 귀속 총량은
문제가 아니었다(로컬 76 vs 정답 72). 모델은 과다 귀속이 아니라 **오배송**을 한다.

관찰된 실패 기전 네 가지:
- (a) 제 집이 있는 이벤트를 옆집에도 넣는다 — 1519(엔화)가 정확한 집("외환시장…")이 있는데
  '금리' 낱말로 두 곳에 더 들어감. "모두 고르라" 는 정방향 압력만 있고 탈락 기준이 없어서다.
- (b) 낱말 겹침 = 귀속 — '경기체감지수' 의 '경기' 가 '기능경기' 에 붙음.
- (c) 술어 맹시 — "전석 독식" 에 여야 분점 사례(정반대)가 들어감. "미달" 에 미달과 무관한
  법안 발의가 들어감.
- (d) 없는 사실 채우기 — "반대 시위" 가 이벤트에 존재하지 않는데 귀속됨.

1단계는 원인이 아니라 증폭기다: 커버리지 구멍(정답 축 "법안 발의", "공단 사업" 이 로컬에 없어
그 이벤트들이 가장 비슷한 이름으로 덤핑)과 **판단형 이름**("~미달", "~독식" — 정답은 대상·쟁점형
"의무고용률 이행과 고용부담금")이 오귀속의 원재료를 공급한다. 1단계와 2단계의 지시가 반대로
당기고 있었다: 1단계는 좁고 주장적으로, 2단계는 "모두 고르라" 로 넓게.

**적용한 처방 (t1-c):**
1. 귀속을 (이벤트, 서브토픽) **쌍 단위 예/아니오**로 전환(`--membership pairwise`) — 후보를
   하나만 보여줘 다중 선택의 정방향 압력을 구조적으로 제거. 원문 인용(quote)을 요구하고
   **코드가 원문 대조해 없는 문구면 귀속 폐기**(실패 (d) 결정적 차단).
2. 술어 검사 규칙 — 이름에 상태·평가어(미달·독식·결렬…)가 있으면 그 상태에 해당해야만 통과.
   낱말 다의성 경고("경기" 예시 포함).
3. 관점 이름을 판단형→갈래형으로 (나쁨/좋음 대조쌍 제시).
4. 관점마다 근거 이벤트 2건(based_on) 요구, 2건 미만은 **코드가 폐기**. "앞으로 늘어날 것"
   예외 조항 삭제 — 근거 1건짜리 관점("기능경기 활성화")이 과잉 귀속의 원재료였다.
5. 마지막 점검 절 — 미귀속 이벤트 3건 이상이면 새 관점 추가(커버리지 구멍 대응).

**한계 판단(진단 결론):** 프롬프트 수정만으로 46%→65~75% 예상, 정답 수준(90%+)은 안 된다.
그 너머는 관점 생성을 bottom-up(이벤트별 라벨→클러스터→2건 이상만 승격)으로 바꾸고 임베딩
하위 컷 등 규칙 후처리를 얹는 구조 변경이 필요하다. **판정 단위를 쪼갤수록 좋아진다는 것이
이 실험 전체의 일관된 교훈이다**(b4→b5 per-event, 7차 pairwise).

#### t1-c — pairwise 첫 실행: 정밀도 쪽으로 과교정

| | t0-c (per-event) | t1-c (pairwise) | 정답(참고) |
|---|---|---|---|
| 이벤트당 귀속 | 1.41 | **0.57** | 1.33 |
| 단독 이벤트 | 0% | **48.9%** | ~2% |
| 토픽 60%+ 서브토픽 | 9% | 0% | — |

추가로 두 가지가 깨졌다.
- **based_on 하드컷이 관점을 전멸시켰다.** 모델이 based_on 을 과소 신고한다 — "언론 탄압" 은
  실제 2건짜리 축인데 [1326] 만 적어 폐기됐고, 90005(이재명) 토픽은 서브토픽 0개가 됐다.
  자기 신고를 믿는 규칙은 취약하다. 하드컷을 제거하고 **pairwise 귀속의 실제 결과**가 근거가
  되도록 되돌렸다.
- **temp 0 재시도는 무의미하다.** 90007 이 3회 모두 같은 위치에서 JSON 이 깨졌다 — 같은 입력에
  같은 출력이 나오기 때문이다. 재시도부터는 온도를 0.3 으로 올려 결정성을 깨도록 고쳤다.

교훈: 진단의 처방(쌍 단위 게이트)이 정밀도를 지키는 방향은 맞지만, 커버리지는 관점 발견이
공급해야 한다. 게이트를 조이기만 하면 recall 이 무너진다 — 정밀도(감사 적합률)와 커버리지
(단독 비율)를 **항상 함께** 볼 것.

#### t1-c 재감사 — 쌍 단위 게이트는 정밀도를 지킨다

같은 sonnet 감사 기준: **적합률 46.1% → 74.1%** (20/27). 진단의 예측 범위(65~75%) 그대로다.
트럼프 토픽은 5/5. 남은 부적합의 패턴: "금리 인상과 자금 조달 비용" 같은 **모호한 복합 이름**이
여전히 인접 이벤트를 빨아들이고(2/5), 이름 문제 4건은 전부 1건짜리 서브토픽의 이벤트 요약형.

확정된 그림: **정밀도는 쌍 단위 게이트가, 커버리지는 관점 발견이 책임진다.** t1-c 의 단독 48.9% 는
게이트 탓이 아니라 관점이 부족해서다(감사도 단독 중 명백한 누락은 1건만 지목 — 나머지는 정말
갈 곳이 없다). 다음 수는 진단의 구조 처방 2번: 관점 발견을 bottom-up 으로.

#### 8차 (2026-08-25~26) — bottom-up 확정, 이름 규칙으로 남은 절반

t3-c 가 그 bottom-up 이다. 진단의 예측대로 커버리지를 되찾았다(단독 48.9%→24.1%, 이벤트당
귀속 0.57→1.5 로 정답 1.33 에 근접). 대신 반대쪽이 무너졌다 — 포함관계 35%, 토픽 전체를 덮는
서브토픽 4개(최대 100%). t4-c 는 그 대응으로 넣은 코드 두 개(자카드 0.6 클러스터 사전 병합,
70% 커버리지 컷)를 처음 검증한 실행이고, 60%+ 서브토픽을 4→2 로 줄였지만 최대 100% 와
포함관계 36.8% 는 그대로였다.

**남은 절반은 이름 문제였다.** t4-c 이름 19개 중 10개(53%)가 "동향"으로 끝났고, 3개가 토픽
제목의 재진술이었다(하나는 글자 그대로 복사). 70% 컷이 못 잡은 이유는 층위가 달라서다 —
컷은 **라벨 클러스터 크기**에 걸리는데, 최종 커버리지는 pairwise 귀속이 만든다. 이름이 넓으면
pairwise 가 전부 통과시킨다. 그래서 **이름 단계가 유일한 지렛대**다.

t5-c 에 적용한 것(자세한 프롬프트 문구는 `subtopic_prompt_guide.md` 4.4~4.5):
1. 토픽 제목을 낱말로 쪼개 금지 목록으로 제시 + 대조쌍. 기존의 "바꿔 말한 수준으로 넓으면
   안 된다"는 추상적이라 안 먹혔다.
2. "동향/현황/관련/이슈/문제" 로 끝내지 말 것 — 어느 갈래에나 붙어 이름이 가리키는 게 없어진다.
3. 형제 갈래 목록을 프롬프트에 주입(`sibling_block`). 클러스터를 하나씩 독립으로 보여주니
   옆 갈래와 겹치는지 볼 근거가 없었다.
4. `restates_topic()` — 이름이 토픽 제목과 bigram 0.55 이상이면 코드가 폐기. 실측 분포에서
   재진술 3건이 1.00/0.62/0.60 이고 그 아래가 0.46 이하라 간격이 뚜렷하다.
5. pairwise 의 quote 에 **서브토픽 이름을 베끼지 말 것**. t4-c 폐기 10건 중 5건이 이벤트
   문장이 아니라 서브토픽 이름 복사였다 — 맞는 귀속까지 같이 죽어 90005가 단독 5건이 됐다.

| | t3-c | t4-c | **t5-c** | t6-c(+refine) |
|---|---|---|---|---|
| 서브토픽 | 20 | 19 | 20 | 17 |
| 이벤트당 귀속 | 1.5 | 1.28 | **1.26** | 1.09 |
| 단독 | 24.1% | 29.6% | **25.9%** | 29.6% |
| 1건짜리 | 10.0% | 10.5% | **5.0%** | 5.9% |
| 포함관계 | 35.0% | 36.8% | **30.0%** | 29.4% |
| 최대 커버리지 | 100% | 100% | **86%** | 86% |
| 공허한 접미사 | 10개 | 10개 | **1개** | 1개 |
| 토픽 재진술 | 3개 | 3개 | **0개** | 0개 |

**`--refine` 은 bottom-up 에서도 기각.** 90007의 중복 2개는 합쳤지만, 90003의 "트럼프의 반공
메시지와 정치적 행보"를 "나토 정상회의와 미국의 동맹 정책"에 합쳐 그 토픽을 서브토픽 1개·단독
8/10건으로 무너뜨렸다. 정작 중복이 남은 90002는 불발했다. 합치기 판단은 이름과 reason 만으로는
할 수 없다 — 실제로 다른 이벤트를 담는다는 사실은 귀속 결과를 봐야 안다. b6 의 기각과 결론은
같으나 기전이 다르다.

#### t5-c 감사 — 적합률은 내려갔지만 맞는 귀속은 2.35배가 됐다

t1-c 와 같은 기준으로 t5-c 의 귀속 68쌍을 전수 감사했다
(`eval/results/subtopic-claude-audit-t5c.json`, results/ 는 gitignore 라 수치는 여기에 남긴다).

| | t1-c | **t5-c** |
|---|---|---|
| 적합률 | 74.1% | **69.1%** |
| 귀속 쌍 | 27 | **68** |
| 그중 적합 | 20 | **47** |
| 단독 이벤트 | 48.9% | **25.9%** |

**적합률만 보면 5%p 후퇴지만, 이 비교는 분모가 다르다.** t1-c 는 게이트를 조여 귀속 자체를
27건만 만들었고 이벤트 절반을 단독으로 버렸다. t5-c 는 그 2.5배를 귀속시키면서 정밀도를
5%p 만 잃었다. 사용자가 서브토픽을 눌렀을 때 실제로 보이는 **맞는 이벤트의 수**는 20 → 47 이다.
정밀도와 커버리지를 항상 함께 보라던 t1-c 의 교훈이 여기서 그대로 적용된다 — 어느 한쪽만
인용하면 결론이 뒤집힌다.

토픽별로는 90002가 75%로 가장 높고 90003·90005가 60%로 가장 낮다.

**오귀속은 넓은 이름에 몰려 있다.** 서브토픽이 담는 이벤트 비율로 나눠 보면:

| 서브토픽이 토픽에서 차지하는 비율 | 개수 | 적합률 |
|---|---|---|
| 30% 미만 | 12개 | **85%** (22/26) |
| 30~50% | 4개 | 52% (11/21) |
| 50% 이상 | 4개 | 67% (14/21) |

좁은 이름은 거의 틀리지 않는다("강북구 장애인 복지 서비스 확대" 2/2, "국가인권위 장애인 권리
보호 논의" 2/2, "의무고용률 이행과 부담금 제도" 2/2). 틀리는 건 넓은 이름이다 —
"장애인고용촉진법 이행과 고용률 관리"(44% 커버)가 3/8, "이재명 대통령의 국정 운영과 정책 방향
설정"(71% 커버)이 3/5. **커버리지 30% 는 이름이 너무 넓다는 신호로 쓸 수 있다.**

**적합률이 탐색 품질을 다 담지 못한다는 점도 기록해 둔다.** 90007은 71%로 평균보다 높지만
서브토픽 3개가 사실상 같은 이름이라("지방의회 개원 및 상임위원장 선출" / "…상임위원장 선출과
원 구성 협상" / "…상임위원장 선출과 원 구성") 사용자가 무엇을 눌러도 거의 같은 목록을 본다.
귀속이 맞아도 탐색이 안 되는 경우가 있다 — 중복 지표를 따로 봐야 한다.

다음 수: 겹치는 이름이 t5-c 에도 남아 있다(90002 "서울 외환시장 운영과 환율 변동" vs "외환시장
운영과 환율 전망"은 이벤트 구성이 완전히 같다). 이름 사후 병합이 실패했으므로 **라벨 클러스터링
단계**(`--sim-threshold`)를 손볼 차례다. 커버리지 30% 상한을 이름 단계의 신호로 쓰는 것도 함께.

### 현재 권장 설정

```bash
# 일괄 생성 (토픽이 임계치에 도달했을 때 최초 생성)
python eval/subtopic_v2_harness.py --snapshot <재구성한 스냅샷> --tag <태그> \
    --min-events 7 --mode two-stage --membership pairwise --discovery bottomup --temperature 0

# 증분 (이후 이벤트가 하나씩 들어올 때)
python eval/subtopic_v2_incremental.py --snapshot <재구성한 스냅샷> --tag <태그> \
    --seed 7 --min-events 8 --split-steps --recompact 5 --temperature 0
```

`--refine` 은 쓰지 않는다(b6 은 llm discovery, t6-c 는 bottom-up 에서 각각 기각).
입력 토픽은 반드시 재구성한 것을 쓴다 — 기존 토픽 배정을 그대로 넣으면 프롬프트를 고쳐도
지표가 움직이지 않는다. 프롬프트 작성 규칙은 `subtopic_prompt_guide.md` 에 따로 있다.

#### 증분 경로의 미해결 리스크

- **서브토픽이 단조 증가한다.** i2 는 같은 이벤트 집합에서 36개를 만들어 일괄(27개)보다 33% 많다.
  증분에는 관점을 **없애거나 합치는 단계가 없어서**, 운영 시간이 길어질수록 한 토픽의 서브토픽이
  계속 불어난다. 주기적 재생성(토픽 전체를 다시 일괄 생성)이나 사용 신호 기반 정리가 필요하다.
- **단독 이벤트가 0.0% 로 사라졌다.** 관점이 계속 늘어나니 어떤 이벤트든 갈 곳이 생긴다.
  단독 이벤트는 억지 분류를 막는 안전장치인데 그게 작동하지 않는다는 뜻이다.
- **seed 품질이 이후 전부를 오염시킨다.** 이름 축약이 일괄 33.3% 대 증분 47.2% 다. seed 3개로
  만든 `총격 사고와 정치적 자화자찬` 같은 이름 아래로 이후 FIFA 징계·젤렌스키 통화가 억지로
  들어갔다. 실험 기준(3개)이 만든 문제이므로 **서비스 기준(7개)에서 다시 재야 한다** —
  현재 데이터에 7개 이상 토픽이 4개뿐이라 아직 표본이 부족하다.

### 남은 결함 (로컬 30B 한계)

- **오귀속**: "반공 메시지 강조"에 총격 사고 자화자찬(1325)과 김정은 산책 사진(1346)이 들어갔다.
  근거 문장은 연설 두 건만 언급하는데 귀속은 네 건이다. 근거와 귀속이 어긋나는 패턴이 남아 있다.
- **개별 이벤트 요약형 이름**: "총격 사고 후 자화자찬", "중국 정상 방문 예상" 처럼 관점이 아니라
  이벤트 하나를 요약한 이름이 나온다. 금지 규칙이 프롬프트에 있는데도 나온다.
- **포함관계 15.9%**: 설계상 위반은 아니다(구성이 같아도 관점이 다르면 공존 허용). 다만 탐색
  화면에서 군더더기로 보일 수 있어 사람 판단이 필요하다.
- **perspective 라벨 편중**: 대부분 "역할" 로 찍힌다. 라벨 자체는 분류에 쓰지 않으므로 무해하지만,
  대상·토픽 고유 관점이 실제로 덜 발굴되는지는 따로 봐야 한다.

다음에 볼 것: 라벨 클러스터링 임계(`--sim-threshold`) 튜닝으로 남은 이름 중복 잡기(8차 참고) /
증분의 서브토픽 단조 증가를 막을 정리 단계(주기적 재생성 vs 사용 신호 기반) /
서비스 기준(seed 7개)으로 증분 재측정 — 그러려면 이벤트 7개 이상 토픽 표본을 더 모아야 한다.
