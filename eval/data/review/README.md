# 검수 대기열

`eval/review_worklist.py` 가 만들고 소비하는 디렉터리입니다. `worklist.json` / `worklist.md`
자체는 분류 결과에서 언제든 재생성되므로 git에 넣지 않습니다.

## 왜 하나

정답 파일(`eval/data/constraints/`)의 **cannot-link 제약이 48쌍뿐**입니다. 이벤트 6개에서만
나왔고, 토픽은 0쌍입니다. 그래서 지금 하네스는 **과병합(붙이면 안 될 것을 붙임)을 사실상
측정하지 못합니다.**

이유는 검수 형식의 비대칭입니다.

| 판정 | 만들어지는 제약 | 개수 |
|---|---|---|
| "이 묶음 맞다" | 이벤트 안 **모든 쌍**이 must-link | 기사 N건이면 N(N-1)/2쌍 |
| "이 기사는 빼야 한다" | 뺀 기사 × 남은 기사 = cannot-link | 명시한 만큼만 |

`ok` 49건이 must-link 1,244쌍을 만드는 동안, 제외 판정 6건은 48쌍밖에 못 만들었습니다.
검수자가 `split` 34건으로 과병합을 강하게 지적했는데도 그 판단이 **채점 가능한 형태로는
거의 남지 않았습니다.**

이 도구는 검수 시간을 cannot-link 가 나올 만한 곳에 몰아줍니다.

## 쓰는 법

### 1. 대기열 만들기

```bash
python eval/review_worklist.py build \
    --snapshot eval/results/event-<run-id>-snapshot.json \
    --log      eval/results/event-<run-id>-classifier.log \
    --constraints eval/data/constraints/review_2026-07-20.json \
    --out-dir  eval/data/review
```

`--constraints` 를 주면 **이전 검수와 충돌할 항목을 미리 표시**합니다. 빼먹으면 나중에
merge 단계에서 한꺼번에 거부당하고, 그때는 어느 판단을 되돌려야 하는지 알기 어렵습니다.

`worklist.md`(사람이 읽는 것)와 `worklist.json`(답을 적는 것)이 나옵니다.

### 2. 검수하기

`worklist.json` 의 각 항목에서 `verdict` 를 채웁니다.

| verdict | 뜻 | 추가 입력 |
|---|---|---|
| `correct` | 이 기사들은 모두 같은 사건이다 | — |
| `exclude` | 일부가 다른 사건이다 | `not_belonging` 에 기사 id |
| `unsure` | 판단 유보 (제약을 만들지 않음) | — |

**확신이 없으면 `unsure` 로 두세요.** 틀린 정답은 없는 정답보다 나쁩니다 — 이후 모든 측정이
조용히 틀린 기준으로 채점됩니다.

### 3. 정답에 합치기

```bash
python eval/review_worklist.py merge \
    --reviewed    eval/data/review/worklist.json \
    --constraints eval/data/constraints/review_2026-07-20.json \
    --out         eval/data/constraints/review_<날짜>.json
```

`_review_rounds` 에 이번 라운드 요약이 남습니다. 새 정답 파일은 커밋하세요.

## 읽을 때 조심할 것

### 대기열은 무작위 표본이 아닙니다

의심스러운 것을 골라 담기 때문에, **이 표본으로 잰 충족률은 실제보다 나쁘게 나옵니다.**
그래서 대기열에 무작위 대조군(`selection: "control"`)을 섞어 둡니다. 대조군은
의심스러워 보이지 않아도 건너뛰지 마세요 — 나중에 "진짜 나빠진 것"과 "어려운 것만 본 것"을
가르는 유일한 근거입니다.

### 다수가 ⚠️ 면 기준 기사를 의심하세요

`거리`는 **이 이벤트를 만든 기준 기사(`생성`)와의 거리**입니다. 그래서 다수가 멀다면 다수가
이상한 게 아니라 기준 기사 쪽이 이질적일 수 있습니다. 대기열이 그런 항목에는 경고를
붙입니다. 실제 사례:

> **E1005** — 제목은 "정부는 장흥댐, 나주댐, 주암댐에서 하루 65만톤의 용수를 확보할…"
> 인데, 기사 24건 중 21건이 "광주 군공항 반도체 부지 확정" 이었습니다.
> ⚠️ 가 붙은 21건을 빼는 게 아니라, 기준 기사 쪽을 빼는 게 맞을 수 있습니다.

### 정답이 바뀌면 이전 실행과 비교할 수 없습니다

검수를 반영하면 채점 기준이 바뀌므로, **분류기가 한 줄도 안 바뀌어도 충족률이 움직입니다.**
하네스가 정답 지문(`gold_fingerprint`)을 기록해 두고 기준이 다른 실행끼리는 개선/악화
판정을 보류합니다. 새 정답으로 기준선을 다시 잡은 뒤 비교하세요.

### 어느 분류 결과로 대기열을 만들든 정답은 유효합니다

제약은 **기사 쌍**에 대한 사실("이 두 기사는 같은 사건인가")이라 분류기와 무관합니다.
분류 결과는 "어느 쌍을 들여다볼지" 고르는 데만 쓰입니다. 다만 그 모델의 실패 양상에
검수 노력이 몰리므로, 표본이 한쪽으로 치우친다는 점은 위 대조군으로 보정합니다.

### 단, 정답을 만든 그 실행은 그 정답으로 평가할 수 없습니다

위 항목의 예외입니다. 정답 자체는 유효하지만 **검수 대상이 된 실행을 채점하는 데는 쓸 수
없습니다.** "이건 과병합"이라고 지목한 쌍은 정의상 그 실행에서 100% 위반이기 때문입니다.

2026-08-03 에 토픽 정답을 t003 하나만 보고 만들었더니 t003 의 cannot 충족률이 **0.0%** 로
나왔습니다. 분류가 특별히 나빠서가 아니라 지목한 쌍이 곧 t003 의 구성이어서입니다. 그
정답으로 실행끼리 비교하면 "t003 보다 잘게 쪼갠 쪽"이 자동으로 이깁니다.

두 가지 방법으로 피합니다.

- **새 실행으로 검증한다.** 이벤트 쪽은 e002 를 검수해 만든 정답을 `EVENT_DISTANCE_THRESHOLD`
  를 바꾼 **e003 재실행**에 썼고, 정상 동작했습니다(cannot 39.6 → 58.3%).
- **여러 실행을 각각 검수해 합친다.** 토픽은 t003 과 t005 두 라운드를 검수해 두 설정 모두
  측정 가능하게 만들었습니다.

### 토픽에서는 must 와 cannot 의 평균을 쓰지 마세요

토픽은 잘게 쪼갤수록 cannot 이 오르고 must 가 내려갑니다. 정확히 반대 방향이라 두 값의
평균은 "얼마나 쪼갰나"만 재게 됩니다. 실제로 `TOPIC_SUBTOPIC_SIM_THRESHOLD=0.65` 가
cannot 93.8% 로 가장 좋아 보였지만, 서브토픽 49개 중 대부분이 이벤트 1개짜리였습니다
(R-S1 97.4% — 서브토픽이 이벤트 복사본).

`rubric_checks.py` 의 **R-S1(단일이벤트 서브토픽 비율)** 과 **R-T1(중복 토픽)** 을 반드시
함께 보세요.

## 토픽 검수 (`--unit topic`)

이벤트 검수가 "이 기사가 이 이벤트에 속하나"를 묻는다면, 토픽 검수는 **"이 이벤트가 이
토픽에 속하나"** 를 묻습니다. 구조는 같고 구성원만 다릅니다.

```bash
python eval/review_worklist.py build --unit topic \
    --snapshot eval/results/topic-<run-id>-snapshot.json \
    --log      eval/results/topic-<run-id>-classifier.log \
    --constraints eval/data/constraints/review_2026-08-03-derived.json \
    --out-dir  eval/data/review-topic
```

`not_belonging` 에는 **이벤트 id** 를 적습니다(기사 id 가 아닙니다). `merge` 는 `unit` 을
보고 `topic_constraints` 쪽에 넣으므로 명령은 이벤트와 같습니다.

제약 파일이 기사 id 로만 되어 있어서, 판정은 이벤트 단위로 받고 저장할 때 기사 쌍으로
펼칩니다. 이때 **이벤트당 대표 기사 3건**만 씁니다(`SAMPLE_PER_EVENT`). 전수로 펼치면 기사
20건짜리 이벤트 둘만 갈라도 400쌍이 나와 큰 토픽 하나가 지표를 통째로 지배합니다. 같은
이벤트 안의 기사 쌍은 이벤트 제약이 이미 다루므로 만들지 않습니다.

> 토픽은 이벤트보다 큰 바구니입니다. 이벤트 검수보다 관대하게 보세요 — "같은 사건"이 아니라
> "같은 이슈"면 같은 토픽입니다. 홈플러스 회생절차와 카드대금 지급보류는 다른 사건이지만
> 같은 토픽입니다.
